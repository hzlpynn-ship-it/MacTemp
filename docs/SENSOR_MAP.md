# M4 MacBook Air 温度传感器实测图谱（SENSOR_MAP）

> 实测机器：MacBook Air M4（Mac16,12，4P+6E / 10 核 GPU / 24GB，无风扇），macOS 15.6.1 arm64
> 实测时间：2026-11-11 08:52–08:57（主实验）、09:00–09:06（HID 交叉验证）
> 产物：`research/sensor_catalog_m4.json`（50 个传感器条目）+ 本文件；复现脚本见 `research/{build_tools.sh,run_experiment.sh,analyze_experiment.py}`
> 结论速览：**flt 键必须按小端 float 解码**；**12 个 ioft 类型的 T 键无法用标准类型解码，建议整体排除**；**Ta0\*/Tz\*** 为占位键；GPU 键会偶发 0.1 / -4.5°C 毛刺，App 必须做范围过滤。

---

## 1. 调查方法

### 1.1 只读 SMC 访问层
自写 `research/smc_mt.{h,c}`：`IOServiceGetMatchingService("AppleSMC")` → `IOServiceOpen` →
`IOConnectCallStructMethod(2, ...)`，与开源工具 smctemp 相同的两个命令（`READ_KEYINFO`=9 / `READ_BYTES`=5）。
不需要 root、不写 SMC、不改系统设置。解码规则（**均已实测校准**）：

| 类型 | 字节序 / 公式 | 备注 |
|---|---|---|
| `flt ` | 4 字节 **小端 IEEE-754**（`memcpy` 读 float） | 本机全部 188 个温度键中绝大多数为此类型；大端解码会得到 1e23 量级的垃圾值（早期探针的 bug 即此） |
| `sp78` | 2 字节大端有符号 /256 | 本机温度键未使用 |
| `fpe2` | 2 字节大端无符号 /4 | 风扇键（本机无 F* 键） |
| `ioft` | **未确认**，8 字节，`smctemp` 也不解码（返回 0） | 12 个 T 键：`TG0B/TG0C/TG0H/TG0V/TG1B/TG2B/TR0Z/TR1d..TR5d`，**排除**（见 §6） |

### 1.2 负载与采样工具（全部在 `research/`，可复现）
| 工具 | 作用 |
|---|---|
| `mt_sampler.c` | 枚举全部 2148 键，筛出 200 个 T\* 键 + 12 个功耗键，0.5s 采样写长表 CSV |
| `cpu_load.c` | `pthread_attr_set_qos_class_np`：`USER_INTERACTIVE` 只压 P 核 / `BACKGROUND` 只压 E 核 |
| `cpu_watch.c` | `host_processor_info` 每逻辑核占用率（1s/次），验证负载是否落在目标簇 |
| `metal_load.swift` | 运行时编译 MSL kernel，30000+ 线程组连续 dispatch，制造 GPU 负载（无 Xcode，仅 CLT 可行） |
| `mem_load.c` | 3GB 匿名内存按 cache line 跨步读写（内存带宽负载） |
| `hid_sensors.c` | 用 dlsym 绑定 `IOHIDEventSystemClient*`，读 HID 温度（`PMU tdie*`、`gas gauge battery`、`NAND CH0 temp`）作为**独立 ground truth** |
| `proc_watch.c` | 环境噪声诊断（可替代被沙盒禁用的 `ps/top`） |

### 1.3 实验设计（单次连续 300s，`run_experiment.sh`）
| 阶段 | 时长 | 内容 |
|---|---|---|
| baseline | 22.4s | 不加自建负载，取环境基线 |
| p1–p4 | 4×20.2s | 4 线程 `USER_INTERACTIVE` 自旋（压 P 核） |
| e1–e4 | 4×20.2s | 6 线程 `BACKGROUND` 自旋（压 E 核） |
| quiet1 / quiet2 / quiet3 | 8.1 / 8.1 / 7.1s | 回落 |
| gpu | 36.6s | Metal 计算空转 |
| mem | 28.2s | 3GB 跨步读写 |
| nand | 0.9s | 1GB `dd conv=fsync` 顺序写 |
| tail | 8.1s | 收尾 |

自建负载合计约 226s（**< 5 分钟上限**）；结束脚本自动等待全部负载进程退出，无残留。
采样：SMC 0.5s/次（192 个可解码键 × 524 样本）；CPU 占用 1s/次。

### 1.4 环境噪声（重要，如实记录）
本机**不存在真正的空载窗口**：用户同时运行 WorkBuddy(Electron)、Codex、Parallels、多个 next dev / node 服务等。
实验期间 `vm.loadavg` = 14.3 → 26.3 → 21.1；`host_processor_info` 显示 10 个逻辑核经常 80–100% 占用。
因此所有结论都用**相对差值**（同一次实验中 P 核负载 / E 核负载 / GPU / 内存 / NAND 阶段相对本次 baseline 的 ΔT 中位值）判定，
而不是绝对温度。`pmset -g therm` 全程未记录到热降频告警。
实验窗口内暂停了并行编译，进一步降低噪声（仍有外部负载不可控）。

另外发现一个关键环境事实：**基线期间 E 簇（见 §3.1 的核序号推断）已被后台负载压到 100%，而 P 簇较闲**，
这导致"E 核只压"阶段无法真正制造"E 簇空闲→满载"对比（后台已占满），只压 E 核的 6 个线程会外溢到 P 簇。
这限制了 E 核传感器的独立判定强度（见 §6 不确定性）。

## 3. Tp / Te 键归属与每核对应关系（核心问题）

### 3.1 先解决"核序号"这一环境问题
- `sysctl hw.perflevel0.logicalcpu=4`、`hw.perflevel1.logicalcpu=6` → 4P + 6E。
- QoS 有效性实测：单线程同一自旋循环，`USER_INTERACTIVE` 725 iters/s vs `BACKGROUND` 363 iters/s，**2.0 倍** → QoS 确实把线程调度到不同性能簇。
- 核序号映射：无法在满载环境下干净判定。可观察的线索是基线时 `cpu0–cpu5` 恒为 ~100%、`cpu6–cpu9` 很低，
  呈现 **6+4 分界**且恰好等于 E/P 核数；按 asitop 等工具惯例（逻辑核 0..E-1 为 E 簇），推断 **E 簇 = cpu0–5、P 簇 = cpu6–9**。
  只压 P 核（UI QoS）时 `cpu6–8` 占用上升 +21~31%，与该推断一致；但 E 阶段线程外溢到 P 簇，数据不能作为强证据。

### 3.2 Tp / Te 键的"三元组 + 恒定温差"结构（本机实测发现）
对 192 个可解码温度键做两两差值的时间序列分析（`std(ΔT)<0.12°C` 判为同源），得到清晰结构：

- **Tp 家族（39 键）= 11 组"三元组" + 2 组双键**。典型三元组 `(x0, x1, x2)` 中：
  - `x0 = x1 − 7.10°C`（恒定，std 0.01–0.03°C）→ x0/x1 是**同一物理传感器的两种校准读数**；
  - `x2` 与 x1 动态相关但不等（线性拟合残差 ~0.8°C）→ 疑为滤波/聚合读数（同族"热"成员）。
  例：`Tp00=Tp01−7.10`、`Tp04=Tp05−7.10`、`Tp0C=Tp0D−7.10`、`Tp1A=Tp1B−8.30`、`Tp1E=Tp1F=Tp3S`（完全同值）。
- **Te 家族（16 键）= 4 组三元组 + 其余**：`(Te04,Te05,Te06)`、`(Te08,Te09,Te0A)`、`(Te0G,Te0H,Te0I)` 中
  首两个恒差 6.7°C、第三个比第二个高 ~3.9°C；另 `Te0R=Te0S−6.70`、`Te0T/Te0X` 同源、`Te06=Te0V` 同值。
- **交叉验证外部键表**：[Stats](https://github.com/exelban/stats) 的 M4 键表把 **Tp01/Tp05/Tp09/Tp0D/Tp0V/Tp0Y/Tp0b/Tp0e**
  标为 performance core 1–8（正好是 8 个三元组的 x1 成员），把 **Te05/Te0S/Te09/Te0H** 标为 efficiency core 1–4
  （正好是 Te 前 4 个三元组的对应成员）。本机是 4P+6E 的基础款 M4，故取**前 4 个 P 三元组 + 前 6 个 E 信号**。

### 3.3 结论：每核推荐代表键
| 物理核 | 推荐代表键 | 同源别名（同传感器不同校准，勿重复展示） | 置信度 |
|---|---|---|---|
| P 核 1 | `Tp01` | `Tp00`(=Tp01−7.1) | medium |
| P 核 2 | `Tp05` | `Tp04` | medium |
| P 核 3 | `Tp09` | `Tp08` | medium |
| P 核 4 | `Tp0D` | `Tp0C` | medium |
| E 核 1 | `Te05` | `Te04` | medium |
| E 核 2 | `Te0S` | `Te0R`（另 `Te0W`） | medium |
| E 核 3 | `Te09` | `Te08` | medium |
| E 核 4 | `Te0H` | `Te0G` | medium |
| E 核 5 | `Te0V` | `Te06` | low |
| E 核 6 | `Te0X` | `Te0T` | low |

- P 核序号依据 Stats M4 键表顺序（perf core 1→4 依次 Tp01/Tp05/Tp09/Tp0D），**没有与物理核编号做硬件级对照**（无 root、无法读 CPU 拓扑寄存器）。
- E 核 1–4 序号完全沿用 Stats 顺序（注意它不是键名字母序：Te05→Te0S→Te09→Te0H）；E 核 5/6 是 Stats 之外的扩展推断。
- 其余 24 个 Tp 键、10 个 Te 键属于**重复传感器/滤波读数/未启用核槽位**（数值全部有效且互相成恒定温差对），
  不建议进 App 传感器列表（否则同一物理核会出现 3 个几乎相同的数值），已在 `sensor_catalog_m4.json` 中剔除；完整清单见 §7。
- CPU 聚合口径：
  - **热点**：`TCMz`（= `Tp1C` = `Tp3T`，全实验 CPU 家族最高值 89–96°C，响应最强）
  - **平均**：`TCMb`（= `TVD0`，中位口径）；若要"平均核心温度"，建议 App 用 `mean(Tp01,Tp05,Tp09,Tp0D,Te05,Te0S,Te09,Te0H,Te0V,Te0X)` 自己算
  - **不要**用 `Ta0*`（全为 0/5 占位）或 `Tz*`（全 0）。

## 5. 交叉验证

| 验证项 | 方法 | 结果 |
|---|---|---|
| CPU 平均口径 | [smctemp](https://github.com/narugit/smctemp) `-c`（M4 口径 = mean(Tp01,Tp09,Tp0f,Tp05,Tp0D)，有效区间 10–120°C） | baseline `-c`=83.4/83.7 vs 本实验 Tp 家族中位 82.8–83.8；P 阶段 `-c`=86.1 vs 本实验 85.1；GPU 阶段 `-c`=88.0 vs 87.0。**一致**（smctemp 混入了 `Tp0f` 这类"热"滤波键，故略高于我们推荐的"每核 x1 成员"均值） |
| GPU 口径 | `smctemp -g`（M4 口径 = mean(Tg0D,Tg0P,Tg0X,Tg0j)） | GPU 阶段 `-g`=83.2 vs 同四键均值 83.1 → **完全一致**；证明 GPU 键解码与聚合口径正确 |
| 电池 | ① HID `gas gauge battery`（多条）② `ioreg AppleSmartBattery` | ① 同刻 HID=31.3/30.2/31.3，SMC `TB0T/TB1T/TB2T`=31.3/30.2/31.3 → **完全一致**；② `Temperature=3023` 按 **0.1K** 换算 = 29.08°C，与当时 TB 组 29–30°C 吻合（**该字段单位是 0.1K，`°C = v/10 − 273.15`**，@collectors 可直接采用） |
| NAND | HID `NAND CH0 temp` | HID=52.0（整数量化、常数） vs SMC `TH0x`=53.9（同刻），差 1.9°C，量级与趋势一致 → 支持 TH0x=NAND |
| 封装/PMU | HID `PMU tdie1..14`（62–70°C）与 SMC `TPD*`（64–70°C） | 量级一致，但 45s 静置期各键同步缓慢漂移导致逐条相关性只有 0.2–0.6，**不足以逐键对应**，TPD 具体含义仍标 low |
| 风扇 | 枚举 2148 键中 `F*` 键数量 | **0 个** → 确认无风扇机型，`FanReading` 应为空数组 |

## 6. 已知不确定项与风险

1. **P/E 归属的强度是"medium"而非"high"**：后台负载把 E 簇压满，无法制造"E 簇空闲"对照；`Tp` 与 `Te` 对 P 负载的敏感度之比约 2.3:1（2.31 vs 1.00°C）支持 Tp=P、Te=E，但共享 die 的传导会让 E 键也跟着动。命名依据是 Stats M4 键表 + 键结构，不是硬件级证明。
2. **每核序号未做硬件对照**：没有 root/私有 API 读 CPU 拓扑，P 核序号沿用 Stats 顺序；E 核 5/6 为推断，若发现顺序不对只影响显示顺序、不影响数值正确性。
3. **Tg/Tp 家族的"双校准"现象**：同一物理传感器常以两个键出现（恒定差 4.6/6.7/7.1°C）。App 若把全部键都展示会出现"同核 2–3 个几乎一样的值"。JSON 已做去重，只保留代表键。
4. **GPU 键毛刺**：`Tg0G/Tg0H/Tg0U/Tg0V/Tg0X/Tg0Y/Tg0m/Tg0n` 偶发 `-4.5` 与 `0.1` 的无效读数（观测到 min=-4.5）。**App 必须过滤**（见 §7 范围表），否则曲线会出现断崖。
5. **`ioft` 类型**（12 个 T 键）语义未确认、标准解码器都解不了，已排除；不要再尝试按 flt 解码。
6. **`Ta0*`（12 键）/`Tz1*`（10 键）**：恒为 0 或 5.0 的占位值，已排除；`TVMD/TVMs/TVmd/TVVi=0` 同理。
7. **`Ts*` 家族（28 键）** 全部是 72–80°C 的独立信号但含义未确认（早期"Ts0P=SSD"的猜测已被 HID NAND CH0 数据否定），JSON 只保留 `Ts0P/Ts1P` 两个低速键作为 `other`，其余不进目录。
8. **环境背离**：本次 baseline 是"热机基线"（CPU 已 80–90°C，外部负载持续），因此 JSON 里的 `typicalIdle` 偏保守（偏高）。真·空闲（刚开机/无外部负载）时 CPU 核心会更低（估计 45–65°C），但本机无法测到真正的冷机空闲。
9. 主实验期间 **NAND 写入仅 0.9s**（1GB，SSD 太快），未能观察到 NAND 温升；`TH0x` 的"存储"NAND 结论主要依赖 Stats 键表 + HID 对照。

## 9. 告警阈值建议（UI 参考，基于本机热机实测）

本机是无风扇被动散热，长时间 10 核满载时 CPU 可见 100–103°C、GPU 88°C 且不触发降频告警，
所以"告警阈值"应比 Intel 机器更保守地只提示、不吓人：

| 部件 | 黄色提示 | 橙色告警 | 红色严重 | 依据 |
|---|---|---|---|---|
| CPU（TCMz 热点） | ≥ 90°C | ≥ 98°C | ≥ 105°C | 实测负载区间 89–96.4°C，峰值 103°C |
| CPU 核心均值（TCMb 或自算均值） | ≥ 85°C | ≥ 92°C | ≥ 100°C | 实测 83.8–90°C |
| GPU（Tg0D 或 10 核均值） | ≥ 80°C | ≥ 88°C | ≥ 95°C | 实测 79–88°C |
| 内存（Tm0B） | ≥ 65°C | ≥ 75°C | ≥ 85°C | 实测 56.7–58.5°C（慢变量） |
| NAND（TH0x） | ≥ 65°C | ≥ 75°C | ≥ 85°C | 实测 54–56°C |
| 电池（TB 组） | ≥ 38°C | ≥ 45°C | ≥ 50°C | 实测 28–31°C；电池长期 >45°C 加速老化 |
| Wi-Fi（TW0P） | ≥ 75°C | ≥ 85°C | ≥ 95°C | 实测 56–58°C |
| 机身（TAOL） | ≥ 40°C | ≥ 45°C | ≥ 50°C | 实测 25–27°C（环境） |

UI 配色仍使用应用内置温度色阶（<55 青蓝 / 55–70 绿 / 70–85 黄 / 85–95 橙 / >95 红），
上表只用于"是否弹出告警"。
